# 受付の本人確認結果のTDD記録

## 今回の範囲

[受付API契約](API詳細設計書.md#reception-api)の本人確認では、確認対象を予約メンバーに限定し、確認済み一覧を全体置換します。一部だけの確認も保存できます。全員確認の真偽値は、クライアントから受け取らず予約メンバーとの照合で算出します。

[ユビキタス言語帳](ユビキタス言語帳.md)にある`IdentityVerification`をDomainの値オブジェクトとして実装します。確認者は`TAId`で参照し、確認日時は引数で受け取ります。認証・現在時刻の取得・保存は内部で行いません。

## テストリスト

- [x] 部分確認と確認者・日時を保持する
- [x] 全員を確認したときだけ全員確認済みになる
- [x] 予約外の学生を拒否する
- [x] 確認対象の重複を拒否する
- [x] 学生予約メンバーが空なら拒否する
- [x] 確認済み一覧を全体置換し、古い値を変更しない
- [x] 確認済み一覧の空を許容する
- [x] 値の同一性と不正構築・コピーの経路を確認する

## 接続時に必要な条件

値オブジェクトの成功は受付操作の許可ではありません。利用日当日の確定済み学生予約、未Check-in、認証されたTAと実行者の一致は、後続の予約側ドメイン処理と認証接続で検証します。現在の`BookingStatus`は仕様の`Confirmed/Canceled`と異なるため、この変更では暗黙に読み替えません。

ログインの提供範囲と未ログイン閲覧は[Issue #22](https://github.com/cardamon04/music-studio-reservation/issues/22#issuecomment-5972301281)、保存の運用は[Issue #25](https://github.com/cardamon04/music-studio-reservation/issues/25)の回答待ちです。今回のモデルには、備品数量上限や返却後の追加貸出に関する判断を含めません。受付API、画面、監査保存、イベント発行、再送制御への接続も対象外です。

## 初回実装の実行記録（2026-10-03）

Red・Greenを実測した順に追記します。最初から成功した境界確認は新しいRedとして数えません。

| サイクル | 振る舞い | 実際のRed | Green |
|---|---|---|---|
| 1 | 部分確認と確認者・日時 | `IdentityVerification`と`TAId`が未定義でコンパイル失敗 | 値を保持する最小実装。1件成功 |
| 2 | 全員確認の算出 | 全員指定しても`false`で失敗 | 予約メンバーとの集合一致を算出。2件成功 |
| 3 | 予約外の学生の拒否 | 人数が同じでも予約外学生を受理して失敗 | メンバーの部分集合かを検証。3件成功 |
| 4 | 重複確認の拒否 | 重複が集合化で消され成功扱いとなり失敗 | 重複指定を明示的なエラーにする。4件成功 |
| 5 | 空の学生予約の拒否 | 空メンバー・空確認が受理されて失敗 | メンバー1名以上を検証。5件成功 |
| 6 | 一覧と確認者・日時の全体置換 | `replace`が未定義でコンパイル失敗 | 同じメンバー集合で再検証し、新しい値を返す。6件成功 |

続けて、不正なコピーが実行時に拒否されることを確認しようとしましたが、`copy`自体が非公開のためコンパイルできませんでした。アクセス可能だというテストの前提を訂正し、構築・`apply`・`copy`を外部から呼べないことを確認しました。確認済み一覧の空、置換失敗時の元の値の保持、値としての等価性も既存実装で成功しています。この4件は新しいRed/Greenサイクルに数えず、本人確認のテストは計10件です。

Refactorでは確認対象の集合化を1回にまとめ、生成・置換の契約をコードに明示しました。唯一の生成口でメンバー1名以上・重複なし・予約メンバーへの所属を検証し、生成後の値は変更しません。

## 初回実装の設計判断

| 設計 | 根拠と責務 | 制約 |
|---|---|---|
| PROP-identity-verification | 既存の言語帳が定める値オブジェクトとして、本人確認対象の整合と全員確認の算出をDomainに置く | 予約から取得したメンバー集合に対する結果。認証や予約状態の判定は含まない |
| PROP-replacement-contract | API本文を確認済み一覧の全体として扱い、新しい確認者・日時とともに置換する | 現在時刻を取得せず、永続化やイベント発行もしない |
| PROP-member-contract | 学生予約のメンバー1名以上を守り、空集合同士の一致を全員確認としない | 学生予約以外のAPI上の`allMembersVerified=null`は、この学生向けモデルの外で扱う |

`TAId`はUUIDを包む識別子で、TA権限を持つ証明ではありません。`IdentityVerification`はケースクラスの値等価性を利用し、privateコンストラクタにより直接生成とコピーを非公開にしています。Scala 3.4.3でそのアクセス制約もテストしています。予約のメンバーが変更された場合は、新しい予約内容を使って本人確認結果を再検証する必要があります。

## レビュー対応後の設計（2026-10-31）

[Set型への依存に関する指摘](https://github.com/cardamon04/music-studio-reservation/pull/30#discussion_r4431508593)を受け、本人確認の公開契約と責務を見直しました。以前は`Set[StudentNumber]`を予約メンバーとして受け取り、その非空性まで本人確認側で検証していました。確認済みの集合も公開していたため、テストも集合表現へ依存する形でした。

| 提案ID | 変更と責務 | 根拠・トレードオフ |
|---|---|---|
| PROP-members-value | 既存用語帳の`Members`を実装し、学生予約の1名以上という条件、所属照合、人数を担当させる | 非空条件を型の生成時に保証する。呼び出し側にはMembersへの変換が必要になる |
| PROP-verification-query | 本人確認はMembersを受け取り、確認済み集合を非公開にする。結果は`isVerified`と`allMembersVerified`で読む | Setは内部表現として残す。外側で集合演算を組み立てず、本人確認の振る舞いを問い合わせる |

`Members.from`は既存データとの境界で集合を受け取ります。Setそのものを禁止する変更ではありません。集合の別名だけを付ける案では非空条件の担当が変わらないため、生成口を持つ値オブジェクトにしました。確認済み側は0名を許容するためMembersを流用せず、本人確認の内部状態として保持します。追加のコレクション型は作っていません。

確認対象の重複と予約外の学生は`IdentityVerification.record`で拒否します。確認済みの全員がMembersに所属することを検証したうえで、人数がそろったかを算出します。全体置換も同じ生成口で再検証し、確認者・日時とともに新しい値を返す契約です。認証や現在時刻取得などの副作用は追加していません。

集合の名前付きアクセサは非公開にしています。ケースクラスの汎用的なProduct操作まで遮断する設計ではなく、業務コードが利用する公開契約を整理したものです。

用語は既存の「メンバー（Members）」「本人確認（IdentityVerification）」と一致し、新語の登録はありません。既存BookingのListをMembersへ変更する作業、受付APIへの接続、他のPRの承認モデルへの適用は今回含めません。

手順は[t-wada氏によるKent BeckのTDD定義の翻訳](https://t-wada.hatenablog.jp/entry/canon-tdd-by-kent-beck)を参照しました。日本語表記は今回のユーザー指示に基づきます。テストを日本語にしただけでTDDを実施したとは扱いません。
