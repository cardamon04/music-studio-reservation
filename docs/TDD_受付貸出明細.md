# 受付の貸出明細のTDD記録

根拠は[受付API契約](API詳細設計書.md#reception-api)とREQ-024です。予約数量・累計貸出数量・累計返却数量の不変条件を先に実装し、認証や保存先に依存する受付APIへの接続は保留します。

## テストリスト

- [x] 引当数量以内を貸出し、元の明細を変更しない
- [x] 分割した貸出を累計し、予約数量を超える貸出を拒否する
- [x] 分割した返却を累計し、元の明細を変更しない
- [x] 未返却数量を超える返却を拒否する
- [x] 貸出・返却の数量が0以下なら拒否する
- [ ] 返却しても累計貸出数量を減らさず、同じ予約へ再貸出しない
- [ ] 構築・コピーで不正な累計数量を作れない
- [ ] 整数の上限付近でも累計がオーバーフローしない

## 回答待ち

[Issue #26](https://github.com/cardamon04/music-studio-reservation/issues/26)で、既存`Quantity`の100個上限の採否を確認しています。明細の累計計算は予約数量を上限とし、既存の予約入力の上限や型は変更しません。

分割返却のテストから、返却後に未貸出の残数を追加で渡せるかが未確定だと分かりました。[Issue #28](https://github.com/cardamon04/music-studio-reservation/issues/28)で、予約全体を禁止するか、返却した備品だけ禁止するか、未貸出分は許可するかを確認しています。数量計算の成功を操作許可とは扱いません。

受付APIに必要な認証、予約状態・利用日の判定、operationIdによる再送制御、監査、永続化、並行更新、引当在庫との連携はこの単体実装の対象外です。[Issue #22](https://github.com/cardamon04/music-studio-reservation/issues/22)と[Issue #25](https://github.com/cardamon04/music-studio-reservation/issues/25)の回答後に接続します。

## 実行記録

変更前の`sbt test`は既存3件が成功しました。以下に一つずつ実行したRed・Greenと設計の変更を追記します。

| サイクル | 追加した振る舞い | 実際のRed | 最小限のGreen |
|---|---|---|---|
| 1 | 1個の貸出と元の明細の保持 | `LoanLine`が未定義でコンパイル失敗 | 明細を追加し、累計貸出数量を加えたコピーを返す。1件成功 |
| 2 | 分割貸出と予約数量の上限 | 3個貸出後の追加1個が成功してしまい、`isLeft`の期待値で失敗 | 未貸出数との差で上限を検証。2件成功 |
| 3 | 分割返却と元の明細の保持 | `returnEquipment`が未定義でコンパイル失敗 | 累計返却数量を加えたコピーを返す。3件成功 |
| 4 | 未返却数を超える返却の拒否 | 2個貸出・1個返却後に2個返却できてしまい失敗 | 貸出累計と返却累計の差で上限を検証。4件成功 |
| 5 | 0以下の貸出数量の拒否 | 0個の貸出が成功してしまい失敗 | 正の数量を検証。5件成功 |
| 6 | 0以下の返却数量の拒否 | 0個の返却が成功してしまい失敗 | 正の数量を検証。6件成功 |

ユーザーからIssue本文の改稿を優先する指示があったため、サイクル6のGreenで実装を一時停止しました。残りの境界値テスト、Refactor、最終状態の全テスト、コードの独立レビューは未完了です。現時点のコードは公開用の完成物ではありません。
