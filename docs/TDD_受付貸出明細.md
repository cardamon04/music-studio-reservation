# 受付の貸出明細のTDD記録

根拠は[受付API契約](API詳細設計書.md#reception-api)とREQ-024です。予約数量・累計貸出数量・累計返却数量の不変条件を先に実装し、認証や保存先に依存する受付APIへの接続は保留します。

## テストリスト

- [x] 引当数量以内を貸出し、元の明細を変更しない
- [x] 分割した貸出を累計し、予約数量を超える貸出を拒否する
- [x] 分割した返却を累計し、元の明細を変更しない
- [x] 未返却数量を超える返却を拒否する
- [x] 貸出・返却の数量が0以下なら拒否する
- [x] 全量貸出後に返却しても、返却済み数量を使って再貸出できない
- [x] 構築・コピーで不正な累計数量を作れない
- [x] 整数の上限付近でも累計がオーバーフローしない
- [x] 未貸出の明細では返却できない
- [x] 数量の不変条件の0境界では正の貸出・返却ができない

## 回答待ち

[Issue #26](https://github.com/cardamon04/music-studio-reservation/issues/26)で、既存`Quantity`の100個上限の採否を確認しています。明細の累計計算は予約数量を上限とし、既存の予約入力の上限や型は変更しません。

分割返却のテストから、返却後に未貸出の残数を追加で渡せるかが未確定だと分かりました。[Issue #28](https://github.com/cardamon04/music-studio-reservation/issues/28)で、予約全体を禁止するか、返却した備品だけ禁止するか、未貸出分は許可するかを確認しています。数量計算の成功を操作許可とは扱いません。

受付APIに必要な認証、予約状態・利用日の判定、operationIdによる再送制御、監査、永続化、並行更新、引当在庫との連携はこの単体実装の対象外です。[Issue #22の回答](https://github.com/cardamon04/music-studio-reservation/issues/22#issuecomment-5972204958)で、システムに登録したアカウントのGoogle認証、TA権限・TAIdの教務部または総務部による管理、端末を問わない権限確認が確定しました。初回の利用者区分と未ログイン時の公開範囲は追加質問中です。[Issue #25](https://github.com/cardamon04/music-studio-reservation/issues/25)の引当・永続化も未回答のため、接続は保留します。

## 実行記録

変更前の`sbt test`は既存3件が成功しました。以下に一つずつ実行したRed・Greenと設計の変更を追記します。

| サイクル | 追加した振る舞い | 実際のRed | 最小限のGreen |
|---|---|---|---|
| 1 | 1個の貸出と元の明細の保持 | `LoanLine`が未定義でコンパイル失敗 | 明細を追加し、累計貸出数量を加えたコピーを返す。1件成功 |
| 2 | 分割貸出と予約数量の上限 | 3個貸出後の追加1個が成功してしまい、`isLeft`の期待値で失敗 | 未貸出数との差で上限を検証。2件成功 |
| 3 | 分割返却と元の明細の保持 | `returnEquipment`が未定義でコンパイル失敗 | 累計返却数量を加えたコピーを返す。3件成功 |
| 4 | 未返却数を超える返却の拒否 | 2個貸出・1個返却後に2個返却できてしまい失敗 | 貸出累計と返却累計の差で上限を検証。4件成功 |
| 5 | 0以下の貸出数量の拒否 | 0個の貸出が成功してしまい失敗 | 正の数量を検証。5件成功 |
| 6 | 0以下の返却数量の拒否 | 0個の返却が成功してしまい失敗 | 正の数量を検証。6件成功 |
| 7 | 負の予約数量の拒否 | `IllegalArgumentException`が発生せず失敗 | 構築時に非負条件を検証。7件成功 |
| 8 | 外部からの累計指定・コピーを禁止 | 任意の累計を指定するコードがコンパイルでき、期待値に反して失敗 | コンストラクタを非公開にし、累計0の生成と貸出・返却のみ公開。8件成功 |

サイクル6で文章改稿のため一時停止した後、7・8を実施しました。続けて、全量貸出後の返却、未貸出での返却、0境界、`Int.MaxValue`付近の計算を追加確認しました。この4件は最初から成功したため、新しいRedとして数えません。明細のテストは計12件です。

Refactorでは全数量の不変条件を非公開コンストラクタに明示し、更新処理と公開契約を整理しました。加算前に残数との差で上限を確認するため、合計値を先に計算してオーバーフローする経路はありません。

## 設計の区切り

| 設計 | 責務と根拠 | 制約 |
|---|---|---|
| PROP-loan-line | `LoanLine`は既存の用語どおり予約・備品ごとの貸出記録。`BookingId`と`EquipmentId`で対象を参照し、数量の不変条件をDomain内に置く | HTTP、認証、保存、時刻に依存しない。予約全体の受付処理やトランザクションの完成を意味しない |
| PROP-cumulative-encapsulation | 累計は外部から指定できず、初期値0から貸出・返却で増加する。元の明細を変えず新しい明細を返す | 永続化からの復元口はまだ追加しない。保存先の決定後に契約を設計する |

数量間の関係はこの明細に閉じ込め、数量を扱う別の層に検証を分散させません。既存`Quantity`は1〜100を要求するため、0を含む累計には使っていません。数量の読み出しと操作引数には`Int`を使いますが、予約入力の100個上限を撤廃する変更ではありません。0や整数最大値のテストも、予約が業務上受理されることを示しません。

返却後の未貸出残数については、数量計算と操作許可を分けています。受付を接続するときは、認証結果をApplicationで受け取り、予約状態などの業務条件をDomainの判定に委譲し、保存を調停する設計が必要です。#28のどの選択肢も、この変更では確定しません。

## 再実行方法

`studio-backend`で`sbt test`を実行すると既存分を含む全テストを確認できます。明細だけを確認する場合は`sbt "testOnly domain.equipment.LoanLineSpec"`です。Scalaのコンパイルも行われます。フロントエンドは変更していません。CIは未設定で、ローカルのテスト成功をCI成功とは扱いません。
