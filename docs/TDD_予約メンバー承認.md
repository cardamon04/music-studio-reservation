# 予約メンバー承認の照合とTDD記録

## 根拠と実装の区切り

[Issue23の本人回答](https://github.com/cardamon04/music-studio-reservation/issues/23#issuecomment-5972740105)で、予約メンバー全員へのメール通知と、全員承認後の予約完了が必要になりました。旧資料の「作成時即確定・承認待ちなし」との相違を要件定義・言語帳・API設計・画面設計に反映しています。

今回の`BookingMemberApprovals`は、取得済みの対象メンバー集合と承認済み集合を照合する不変の値です。学生予約の対象は1名以上で、承認済みは対象の部分集合でなければなりません。対象外の学生を数えず、全員が一致したときだけ`allMembersApproved`が真になります。

これは予約確定の十分条件でも、承認操作そのものでもありません。本人の認証、作成者の自動承認、承認の撤回・拒否、期限、メール送信、保存、枠・在庫確保、予約状態遷移は含みません。承認待ちの詳細は[Issue31](https://github.com/cardamon04/music-studio-reservation/issues/31)、変更と再承認は[Issue32](https://github.com/cardamon04/music-studio-reservation/issues/32)の回答後に設計します。

既存の`Booking.complete()`は今回の承認完了へ流用しません。現行カレンダーでは`Completed`が`InUse`へ変換されており、新しい承認状態とは関係のない既存表現です。受付での学生証確認`IdentityVerification`も、予約への同意とは別です。

## テストリストと実測結果

- [x] 全員の承認がそろった場合だけ全員承認とする

- [x] 空の対象メンバーを拒否する
- [x] 対象1名の境界を確認する
- [x] 値等価性と、別の結果を作っても元の値を変更しないことを確認する
- [x] 外部構築・コピー・全員承認フラグの直接指定を許さない

最終の`sbt test`は10件成功しました。内訳は承認照合7件と既存のHomeController 3件です。Red/Greenの各ログと最終結果は作業記録の`approvals-01-red.log`〜`approvals-05-boundaries-all.log`に保存しています。

## 用語と設計判断

指定のDDDスキルを使う独立設計レビューで、承認済み集合の照合は未決の状態遷移から独立して実装できると判断しました。`PROP-member-approvals`としてDomainに所属検証と全員一致の算出を置きます。外側の層・時刻・通知に依存せず、引数を変更しません。

言語帳管理スキルで正本を更新しました。「メンバー承認」「全員承認」は確認済みの条件と未決の操作契約を分けて暫定登録し、「予約申請」「承認待ち」「予約完了」は状態・意味の詳細を確認する保留項目として記録しています。英語の新しい業務呼称を独断で確定していません。コードの物理名と業務語の登録状態も分けています。

「本人確認」は学生証提示の記録、「認証」はログインするアカウントの確認、「操作権限」は対象操作を許されるかの条件です。取消と物理削除、返却済み数量の再貸出と未貸出残数の追加貸出も区別し、Issue22・24・28の未回答部分は実装の前提にしていません。
